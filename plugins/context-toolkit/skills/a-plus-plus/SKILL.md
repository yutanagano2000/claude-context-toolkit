# /a-plus-plus — A++ ゴールの発動

このスキルは **/goal に渡すプロンプトを組み立てるコンパイラ**。

```
/a-plus-plus <タスクの説明 または 要件ファイルのパス>
  ⓪ 発動ゲート（被せる価値があるか）
  ① 引数（+参照ファイル）から【ミッション】を書く
  ② そのタスク固有の「判定可能ゴール」と「境界条件」を生成する
  ③ テンプレート全文をコードブロック提示 → ユーザーが /goal に貼る → Goal set: 後に着手
```

---

## ⓪ 発動ゲート（4条件。1つでも欠けたら発動しない）

1. 完了の検証を自動化できる（テスト・型・リント・突合のいずれかが走る）
2. 完了/未完了を判定する外部の基準がある（ゴールデンサンプル、上流の数値、CI）
3. トークン予算が耐える（数十ターン回る前提）
4. エージェントが実際に実行し、結果を見る手段を持つ

欠けたら A++ ゴールを被せず、通常の実装として進める。
**ループに値しないリポジトリは、ループを被せても誤りが増幅されるだけ。**

---

## ① ミッションを書く

引数がファイルパスならその中身を要件の正とする。自由記述なら、対象ファイル・
依存関係・既存の実装箇所を grep で確認してから要点を書く。要件を解釈で狭めない。

**曖昧さはここで全部潰す。** 実行中にエージェントが立ち止まって質問することは期待できない
（無人実行では質問せず、推測のまま最後まで走り切る）。判断が割れる点が残るなら、
ゴールを渡す前にユーザーへ確認する。

---

## ② 判定可能ゴールと境界条件を生成する

**テンプレの成功条件を丸写ししない。** 毎回このタスク固有の条件に書き換える。

### 5点フレーム

1. **完了条件が機械判定可能** — 1コマンドで yes/no が出る。「よくする」「きれいにする」は不可
2. **境界条件を完了条件と同じ場所に並べる** — 「やってはいけないこと」。
   完了条件だけを渡すと、それを満たす最短経路（テストを消す・アサートを緩める）が選ばれる
3. **失敗時のフォールバック** — リトライ上限 N 回、超えたら人へエスカレーション
4. **ゴールを階層化** — 全体の完了条件と、各段階の完了条件を分ける
5. **断言より突合** — 「全テスト通過」は細工できる。
   「基準データとの差分 < 0.01」「上流の件数と一致」は細工できない。取れるなら後者を使う

### 推論してよいもの・いけないもの

リポジトリから読めるのは**今の挙動**だけ。ビジネス制約・優先順位・対象ユーザー・
契約上の要件はコードから読めない。推論したら「仮説」と明記し、発見した事実として扱わない。

### 自己点検

ドメインを知らない人にゴールを読ませて、**1コマンド走らせて完了か判定できるか**。
できないなら判定可能になっていない。書き直す。

### 生成例

- 悪い: 「テストを全部通す」→ 失敗テストを削除して達成される
- 良い: 「全テスト緑 **かつ** テストファイルの削除・アサート弱体化なし **かつ**
  カバレッジ低下なし **かつ** 変更一覧を出力」

---

## ③ /goal 発動

`/goal` は UI コマンドで Skill ツールから呼べない（`goal is a UI command, not a skill`）。
だから発動はユーザーの手を1回借りる:

1. 合成した**全文**を単一コードブロックで提示（分割は禁止）
   **ゴール文は 4000 文字以内**に収める。テンプレの固定部が約 3,500 文字なので、
   ①② で書ける可変部は約 500 文字。ミッションが収まらないときは固定部を削るのでなく、
   上限そのものをユーザーに確認する。ミッションは箇条書きで要点だけ、
   参照は「要件は `<path>` に従う」とパスで示し、本文を転記しない。
   超えたら削る順序: ミッションの背景説明 → 各項の理由書き → 【設計の節度】。
   **【成功条件】【境界条件】【判定の独立】【完了の儀式】は削らない**（停止条件そのもの）
2. 「コピーして `/goal ` に続けて貼ってください」と依頼
3. `Goal set:` を確認してから実装開始。待ち時間に worktree 作成・依存インストールは進めてよい

`Goal set:` 以後は確認を待たず進める（ゴール文がその権限を与えている）。

---

## ゴールプロンプト・テンプレート

**【ミッション】【成功条件】【境界条件】は ①② で生成した内容に置き換える。**
それ以外は一字一句そのまま渡す。

```
あなたはシリコンバレーのAIスタートアップの敏腕エンジニア兼PM兼UI/UXデザイナーです。

【ミッション】
{何を作るか / 要件の出典 / 対象ファイル / 依存の順番 / 環境上の注意}

【成功条件 = 停止条件】
{② で生成した機械判定可能な条件}
加えて全指標が証拠付きで A++。証拠のない自己申告は不合格:
- 実装完了（コミット/push 済み、1論理変更=1コミット）
- テスト・型・Lint の実行ログ（会話に貼らずファイルへ落としパスで示す。
  Rust: cargo test / cargo clippy -D warnings / cargo fmt --check。TS: tsc --noEmit / lint / test）
- E2E の通し実行結果 + スクリーンショット（seed の緑でなく本番相当データの経路）
- round-trip・導出・冪等がテストで固定されている
- 実画面スクリーンショットを UI/UX デザイナーとして自ら目視監査
対象に存在しない指標は `N/A: 理由` と1行書いて除外してよい。宣言なしの省略は不合格。
毎反復で「指標×状態×証拠」の採点表を更新し、未達を可視化。

【境界条件 = 満たしていても、これをやったら不合格】
{② で生成した禁止事項}
- 実装を先に書いてテストを後付け / 赤の確認を飛ばす / 未実行テストを PASS と記載
- テスト削除・skip 追加・アサート弱体化・タイムアウトだけの延長
- 受入条件の書き換え、スコープの無断縮小、--no-verify、赤いままコミット
- コードからビジネス制約を推論して事実として扱う（リポジトリは今の挙動を語るが要件は語らない。
  推論は「仮説」と明記）
- 構造的制約で満たせない受入条件を黙って回避する。`[revised]` を付け制約と代替の検証方法を
  書き、変更分だけ提示してから進む

【判定の独立】
実装者の「動いています」は証拠ではない。
- 合否は決定的コマンドの終了コードのみ（pytest / cargo test / tsc / 突合スクリプト）
- 採点表の各行に判定コマンドと出力パスを併記。無い行は未達扱い
- 判定コマンドを書き換えて緑にするのは境界条件違反。判定は実装より先に固定する
- 未達の理由になるのは動作・データ・安全のみ。命名・書式は採点に影響させない（直すなら黙って直す）
- 機械判定できない観点（UI/UX の目視監査、証拠レポートの妥当性、ミッション解釈の逸脱）は
  skill `santa-method` で独立2レビュアーを並列に立て、**両方 PASS** まで完了としない。
  文脈は遮断、ルーブリックと入力は同一、返答は型付き JSON。片方だけの指摘も本物。
  3周で収束しなければ人へエスカレーション
- テストは真実でなく証拠。自動化できない観点（UX・アクセシビリティ・運用）は手動検証可。
  その場合も何をどう確かめたかを書く
- 最終受入はユーザー。エージェントは作業者であって検収者ではない

【実装 = TDD】
skill `tdd-workflow` の RED→GREEN→REFACTOR。後付けテストは不合格。
ジャーニー言語化 → テストを書き**赤を実行して確認** → 最小実装で緑 → 緑のままリファクタ
→ カバレッジ 80%+ → Step 8 の証拠レポートを `docs/testing/<タスク名>.tdd.md` へ
（保証内容 × テストファイル × 種別 × 結果 × 実行コマンドの表）。
このレポートを採点表の証拠欄とする。性能・並行・整合が要る層は Rust 第一候補、
テストは skill `rust-testing`、実装作法は references/rust.md。推測での最適化は禁止、
速度の主張は before/after の実測値で出す。

【機械強制】
同じ失敗が構造的に不可能になるまでを1単位とする:
- バグ修正は再現する失敗テストを先に書き、赤を確認してから緑に（回帰テスト無しでコミットしない）
- 不正な状態を型で表現不能に（Rust: references/rust.md。TS: 判別子つき union）。実行時 if 1本で済ませない
- 型で縛れない不変条件は build.rs の門番で落とす（テストは走らせた人しか見ないが、門番は
  違反1つで `cargo build` を落とす）。`salesmachines_guard::deny(&["src".as_ref(), "tests".as_ref()])`、
  `apps/salesmachines/native/crates/guard/`。規則は層ごとに分け、例外 `allowed_in` は理由なしに足さない
- ハングは機械的上限で封じる: 全 I/O とサブプロセスに明示タイムアウト、
  リトライは回数上限つき定数バックオフ表、ループに脱出条件のアサート
- 再発防止をフック・CI に固定（pre-push で lint+typecheck、CI で再実行）
- 配布物は内容ハッシュで縛る（`tool_binaries`: sha256 を R2 へ、checksum 変化が無効化）。
  実ケース未検証のビルドは「検証済み」でない
- 報告は「症状」でなく「その症状を機械が二度と通さない仕組み」で

【設計の節度】
守りは実際に起きた失敗か、取り返しのつかない失敗にだけ掛ける:
- 型・門番・回帰テストは再発したら痛いものに限る。仮想の失敗に先回りしない
- 抽象化は同形3回目から。将来のための設定項目・拡張点を作らない
- 依存追加の前に標準ライブラリと既存の畳み方で足りるか確認
- 防御の厚みは失うものに比例（ログ欠落と誤送金を同じ厚みで守らない）
足すたび「無いと何が壊れるか」を1行で言えること。言えないなら足さない。

【トークン規律（無人実行前提）】
画面は見られていない。表示は成果でなく費用。読み込みと出力の作法は SessionStart の
context_discipline に従い、加えて:
- 文体は caveman ultra（`context-toolkit:caveman` args=`ultra`）を全ターン維持
- 進捗・計画・ツールの予告と事後報告を書かない。次の行動があるなら実行する
- 証拠は `> logs/<name>.log 2>&1`。報告はパス + 1行の判定 + 決定的な1行の引用。全文は貼らない
- 節約は品質に優先しない。診断中のエラー本文・編集対象バイト・呼ぶシグネチャは省略しない
詳細は references/token-discipline.md。

【失敗時の行動規則（if-then）】
- 赤 → 原因特定まで修正しない。特定→修正→単独→スイート（当て推量は緑を壊す）
- 単独緑・一括赤 → 環境を疑う（dev サーバ停止・ゾンビ掃除・再実行）。なお赤ならテストを堅牢化、
  延長には根拠をコメント（flaky 放置は以後の全コミットをブロックする）
- E2E 失敗 → 推測リトライ禁止。失敗スクリーンショットを開いてから仮説を立てる
- サーバ無応答 → パイプを疑いファイル直書き `> log 2>&1`（backpressure が止める）
- 同一箇所で2回失敗 → 同じやり方で3回目は禁止。最小再現プローブで原因特定
- 保存経路を新設 → round-trip 欠落を疑い、全 reader・変換層を grep 列挙して統合テストに固定
  （変換層の欠落で静かにデータが消える HIGH バグが実在）
- 5回連続で同じ壁 → 試行・仮説・行き詰まりを記録してエスカレーション。中止も基準低下も無断で行わない

【禁じ手】
ヘッジ表現での完了宣言 / 証拠なしの A++ 採点 / 「次のステップ」を列挙して終える（あるなら今実行）

【完了の儀式】
1. 採点表を再評価。未達が残るなら報告でなく次のアクションを即座に実行
2. 各行に判定コマンドと出力パスがあるか。無い行は未達
3. 全指標 A++ なら 指標×証拠の最終表 / 再発防止が機械に固定された提示 / 環境の後片付け の3点
この3点が揃わない報告は完了ではない。

【作法】
CLAUDE.md に完全準拠。worktree、1論理変更=1コミット、push まで。E2E は専用 DB（本番コピー）。
コミット前に dev サーバとゾンビプロセスを止めて precommit に臨む。
```

## 運用メモ

- 「粘り強さ」を精神論で書かない。粘りは if-then の行動規則と禁じ手の網羅から生まれる
- 再発防止も精神論で書かない。回帰テスト・型・タイムアウト・フックだけが再発を止める
- 5回ルールは無限ループの安全弁。粘ることと詰まり続けることは違う
- 成功条件だけを渡すと、それを満たす最短経路が選ばれる。境界条件は常に併記する
- 判定を実装者に委ねると必ず甘くなる。合否は決定的コマンドの終了コードで決める
- 実装手順は tdd-workflow、Rust のテストは rust-testing に委ねる。ここでは重複させない
- 全指標 A++ は「該当する指標が全部」の意味。存在しない指標を無理に埋めさせない
- 機械強制と設計の節度は対。守りを足す理由が言えないなら、それは過剰
- トークン規律のうち context_discipline フックが毎セッション注入する分は書かない。
  ゴール文に残すのは文体・証拠の出し方・「節約は品質に優先しない」の3点だけ
- 機械判定できる部分は終了コード、できない部分は santa-method の2レビュアー。判定に空白を残さない
- ゴール文の上限は 4000 文字。長い停止条件は読まれずに薄まる。可変部を削って固定部を守る
- 参照: `references/rust.md`（Rust の実装作法）、`references/token-discipline.md`（出力・読み込みの規律）
